# Design

## Context

See proposal.md for motivation. The relevant parts of the current system:

- `GoodFlows.Spry.Sprites` is the only SDK caller. It wraps each action in a supervised task with a wall-clock deadline, guard-kills on caller death, and scrubs the token from errors. Its `exec/4` merges stderr into stdout and keeps only a tail.
- Runs use PgFlow jobs (`RunJob`, `max_attempts: 1`), owner ids of the form `node|boot_id|uuid` (`Executions`), conditional owner-fenced writes, and a leader-elected `ReaperScheduler` (`:global` name) that enqueues sweeps.
- The sprites SDK (0.2.4) has per-sprite checkpoints (`Checkpoint.create_by_name/3`, `restore_by_name/3`; each makes one blocking HTTP request and returns the complete list of parsed NDJSON messages only after the response ends, silently dropping unparseable lines, so nothing is consumed incrementally), `spawn/4` with `:env`, `:dir`, and separate `{:stdout, …}` / `{:stderr, …}` / `{:exit, …}` messages, and `Filesystem.write/4`, which takes a whole binary. `stderr_to_stdout` is honored only by `Sprites.cmd/4`; `spawn/4` always delivers stderr separately. It **cannot create a sprite from another sprite's checkpoint**. `spawn/4` opens stdin only with the undocumented `stdin: true` option (default false), and `Checkpoint.create_by_name/3` returns NDJSON stream messages rather than a checkpoint id; a 2xx stream may still contain `type: "error"` messages.
- The endpoint has only the LiveView socket. `GoodFlowsWeb.Plugs.BodyParsers` already skips parsing for test report uploads, which read their own body after authentication.
- The client is `goodci`, whose scheduler stays local and which replaces its process spawn (`runner.rs` `command()`) with remote execs. Its outputs-file contract (64 KiB, client-validated) and report collector (direct `*.jsonl` in the job's report dir) are fixed points this design serves.

## Goals / Non-Goals

**Goals:**
- Low-latency member grants for agent loops (warm `min_ready`), fair sharing between concurrent invocations, and no leaked members after a client disappears.
- Execs that survive brief network drops without losing their exit status or outputs.
- Reuse the run machinery's safety properties: bounded actions, owner fencing, token never exposed.

**Non-Goals:**
- Sharing files between members or syncing artifacts between jobs. Only the client-visible `outputs` cross jobs.
- Persisting streaming stdout/stderr, log retrieval after the fact, and a dashboard UI. Bounded terminal exit payloads are retained for replay.
- Incremental or rsync-style workspace transfer, and caching workspaces across sessions.
- Repo-defined pool setup and setup fingerprints from clients.
- Autoscaling beyond `max_members` and cost accounting.

## Decisions

### D1. One golden checkpoint per member, not per pool

Each member runs the full setup and checkpoints itself, because the SDK cannot clone a checkpoint onto a new sprite. Members are therefore long-lived. A reset is `restore_by_name(member, golden_id)`. The SDK returns the complete NDJSON message list only after the HTTP response ends, so the `bounded/3` deadline kill is the only timeout; a create or restore that times out has an unknown remote outcome and makes the member `broken`. The checkpoint id lives on the member row and is never exposed. Provisioning passes a unique comment (`gfp-golden:<member_id>:<nonce>`) to checkpoint creation, fails on any `type: "error"` message, and resolves the id by filtering the `Sprites.list_checkpoints/2` result on that comment in GoodFlows (the SDK has no comment filter). Restore also fails on error messages.

*Alternatives:* destroy and recreate per lease (minutes of setup per job, ruled out for agent loops); a single image snapshot (not available in the SDK). If Sprites adds clone-from-checkpoint, only provisioning changes.

### D2. Member state machine with fenced transitions

States: `provisioning → idle → leased → resetting → idle`, with `broken` and `destroying` as exits. Every transition is a conditional `UPDATE … WHERE id = ? AND state = ? [AND owner_id = ?]`, the same fencing as runs, so a slow or zombie worker cannot overwrite a newer state. `stale` is derived (`member.setup_version < pool.setup_version`, or `member.helper_version` older than the server's packaged helper, see below) instead of being stored as a state, so a setup edit is a single pool update. Stale or excess members go from leased directly to destroying on release, never directly to idle. Provisioning captures setup and setup_version under the pool lock; completion records that captured version, and a now-stale result is retired without a grant. `abandoned` is a final state for a member whose sprite could not be destroyed after its fifth failure ending in an authorization error (`401`/`403`: the creation credential was revoked); it is not retried, still counts toward `max_members`, is shown by the API, can be forgotten by an operator (`Pools.Operator.forget_member/1`, with an audit log line), and is forgotten (logged by name) when its pool's deletion completes, so a revoked credential can never block pool or project deletion. The database pins the state vocabulary with a CHECK constraint.

**Helper staleness (review M3).** A member records the helper identity `<version>+p<protocol>` (the manifest's release version and protocol), not a digest of the packaged binaries. A member is stale only when its helper is *older* than this node's: a lower protocol, or the same protocol and a lower SemVer release version (an unparsable version compares by equality). A member with the same or a newer helper is never stale, and a node grants only members whose protocol it speaks. Rationale: the previous identity (binary SHA-256 digest) made every member stale on any rebuild (builds are not bit-for-bit reproducible across hosts and toolchains, and `priv/gf-transfer` is not versioned), and during a rolling deploy old and new nodes retired each other's members back and forth. Comparing versions in one direction gives a monotonic fleet upgrade (bumping `version` in `sprite-transfer/Cargo.toml` is what rolls members), survives rollbacks and rebuilds, and needs no cluster-wide state. The installed binary's SHA-256 is still verified against the manifest entry for the member's architecture at provisioning, before the golden checkpoint. A node without a manifest treats no member as stale. *Alternatives:* a cluster-wide "current helper" row (extra state and a coordination step on every deploy); pinning the toolchain and building once in CI (still churns on any rebuild, and there is no CI here).

### D3. Long member operations are PgFlow jobs; the reconciler only decides

Provision, reset, and destroy each run as their own PgFlow job (`:pool_member_provision`, `:pool_member_reset`, `:pool_member_destroy`; PgFlow's `queue` is a unique job slug), each `max_attempts: 1` with a compile-time hard timeout: provision derives from a new `provision_timeout_ms` budget and reset/destroy from the step timeout, all checked at startup like `Config.validate!/0` does for runs. They are registered in `config/runtime.exs` `jobs:` with env-configurable `worker_options` concurrency so long setups cannot starve `RunJob`. A `PoolReconciler` tick, leader-elected exactly like `ReaperScheduler`, started next to it in `Application.pgflow_children/1`, and running every 15s, plus PubSub nudges on pool change, release, and session demand, computes the deficits from D4 and enqueues jobs. The same tick:

- destroys broken, stale-idle, and excess-idle members, and, for a pool with the opt-in `idle_ttl_ms` (default null: off), idle members idle longer than that (since `idle_since`), longest idle first, while more than `min_ready` plus the unmet wants of open sessions would remain idle,
- expires sessions (D6); the scheduled tick only flips their status and runs the wind-down (exec cancels through the coordinator, member release) in supervised tasks, so a slow coordinator never holds up the pass,
- fails jobs whose owner is gone, using the `Executions` owner lookup; each distinct owner id is probed once per pass, concurrently,
- re-enqueues members left in a job state without an owner, unless PgFlow still has a pending (`started`) run for that member that is younger than the operation's hard deadline,
- deletes ended sessions (and their execs) that ended more than `session_retention_ms` ago (default 30 days, like `Spry.Reaper`'s output retention), in batches.

Each phase and each pool runs isolated: an error is logged and the rest of the pass continues, so one bad pool cannot stop reconciliation of the others. A name collision after the bounded retries skips that admission instead of failing the pass. The provisioning backoff is read from the locked pool row, so a failure recorded after the pass read the pools is honored. Without an account credential no idle member is retired for being in another credential namespace (only stale ones are).

Provision failure streak and `next_provision_at` live on the pool, surviving destruction of a broken member. Marking a provision `broken` and recording the streak happen in one transaction under the pool row lock, so no tick provisions again in between without the backoff; a provision whose worker was lost counts toward the streak like a failed one. Retiring idle members (to `destroying`) runs under the pool row lock too. Member names are inserted with `ON CONFLICT (name) DO NOTHING` and retried, because a failed `INSERT` would abort the surrounding transaction. Success or a setup revision clears the streak; sanitized pool diagnostics expose the backoff even after member removal. Provisioning stops whenever total existing members (including broken and destroying rows) reaches `max_members`. A provisioning member is counted toward capacity as soon as its row exists, so concurrent ticks cannot overshoot `max_members`. The row is inserted under the pool row lock.

*Alternatives:* a GenServer per pool (needs cluster-wide singleton per pool, and state is lost on node death); doing the work inside the tick (blocks other pools for minutes).

### D4. Grants are serialized per pool by a row lock

`grant(pool_id)` runs in a transaction that holds `SELECT … FOR UPDATE` on the pool, then on the candidate session rows, then on the idle member rows; every writer that shares these rows takes the same order (pool, session, member): exec admission, member release, and `member_lost`. Each lease is still conditional on the member being `idle` and the session open (a member taken meanwhile is skipped, a session ended meanwhile is never reopened), and increments `granted_count` in place instead of writing a value read earlier. Sessions past `acquire_deadline_at` with no first grant are not granted. It picks idle, non-stale members whose credential fingerprint matches the session, and orders eligible waiting sessions by `(granted_count = 0) DESC, wanting_since ASC`, which implements the fairness rule. After each individual assignment it updates `wanting_since` to the grant timestamp if demand remains and re-sorts all wanting sessions, using session id as a stable tie-breaker, until no idle members or no wanting sessions remain. It runs on member→idle, session create, and want changes, and on every reconciler tick as a safety net. After commit it broadcasts `member_granted`. Capacity demand for D3 is `min_ready + Σ max(wanted - granted_count, 0)`, with existing leased and resetting members also counted against the hard total cap. `wanted` starts at `max_members` and means desired total holdings. Lowering it does not revoke holdings; explicit `release_member` atomically sets it to `min(wanted, holdings_after_release)`, allowing zero, to avoid replacing an intentionally returned member. Explicit `want` accepts 0 through the session maximum; raising demand starts a fresh waiting interval. `release_member` runs as one session-coordinator call that never blocks the coordinator: it kills the member's in-flight hydration at once, marks the member releasing (no exec is admitted on it meanwhile), and cancels its running exec in a supervised task, asking the ExecServer not to reset the member itself if the kill is unconfirmed (the release resets it); when that task reports back, in one transaction under the pool and session row locks, it releases the member and sets `granted_count` to the number of members still leased (and `wanted` to at most that), then invalidates the member's reports and answers the caller (`GenServer.reply/2`). When the coordinator is unreachable but not confirmed lost, `release_member` is refused (`unavailable`) and the member stays held. Grants triggered from session creation, the coordinator, or channel handlers use a variant that logs a database error and nudges the reconciler instead of raising, so a failed grant never fails a committed session creation or crashes a coordinator. Pool deletion, session creation, and grants share the pool lock; deletion refuses both waiting and active sessions.

### D5. Workspace upload: spool once, write to each member

A supervised session coordinator registered in `Executions` owns the captured credential/SDK client in memory and the node-local workspace spool. Store its boot-fenced `owner_id` on the session. Uploads arriving on another node stream bounded chunks over acknowledged, deadline-bounded owner RPC; hydration of every initial or late grant runs on that owner under the transfer semaphore. Session exec admission and report reads resolve their SDK client through the owner without returning credentials to channels or clients. There is no spool failover: after confirmed coordinator loss, or after disconnect grace when its node is unreachable, expire with `session_owner_lost`, fence the session, cancel execs, and recover members subject to D7 ownership safety. A coordinator unable to renew its DB lease must stop admitting work and discard its resources by that deadline: it keeps the lease deadline it last recorded (measured before each successful renewal), retries a failed renewal (a database error, logged) every second until then, refuses execs and uploads (`unavailable`) once it has passed, and stops. A transient database error in any coordinator callback is logged and answered `owner_unavailable` instead of crashing the coordinator, which would end its sessions. A coordinator whose session row insert fails or raises is stopped by the creator, and one never activated stops itself after 30 s, so it never outlives its row while holding the token. Each renewal also re-queues hydration for any leased member still missing its workspace, so a lost `member_granted` broadcast only delays hydration. Hydration, preflight, report transfers, and the exec cancels of `release_member` and `end_session` run in linked, monitored tasks under `GoodFlows.Spry.TaskSupervisor`; a task that dies without reporting is noticed through its monitor (a hydration counts as failed and the member is reset; a report's waiters get `503`). Join does not revive an ownerless session. Ending a session stops the coordinator and deletes its spool; a startup janitor removes spools of earlier boots, and a periodic sweep (every 10 minutes) removes this boot's session spools whose session is unknown or ended or whose coordinator is no longer registered here.

The workspace route reads the body itself, as test report uploads do: `BodyParsers`, `RequireParsedBody`, and `SentryScrubber` all pass `/api/v1/pool-sessions/:id/workspace` through untouched, through a shared `raw_body_route?/1` predicate generalized from `BodyParsers.test_report_upload?/1`; otherwise `RequireParsedBody` in `:api_write` would answer `415`, and Sentry would fall back to the default body scrubber. Like `TestReportBody`, it checks in order: `415` unless Content-Type is `application/gzip` and Content-Encoding is absent or `identity`; `413` when a declared Content-Length exceeds `workspace_max_bytes`, before reserving; `503` with `Retry-After` when the node spool budget or a per-account concurrent-upload cap (default 1, enforced per node rather than cluster-wide, since it protects each node's disk) is exhausted; `408` after `workspace_read_timeout_ms` (default 300 s) overall read deadline, releasing the reservation and leaving the upload retryable; then `413` when a chunked body passes the limit. It streams to the coordinator's disk spool up to `workspace_max_bytes` (default 256 MiB). Admission reserves `workspace_max_bytes` from the node-wide `spool_max_bytes` budget and from the account's `spool_account_max_bytes` share of it (default 1 GiB, at least `workspace_max_bytes`; uploads and report downloads together, so one account cannot starve the others) and responds `503` with `Retry-After` when it cannot. Once the upload is recorded, its reservation shrinks to the archive's actual size (and frees the account's upload slot) for as long as the spooled archive is kept. A body that cannot be read is `400`. Preflight validates complete archive entry metadata, links, expanded size, entry count, and wall-clock bounds before any member hydration; invalid archives respond `422`, limit breaches `413`, and remain retryable. The compressed spool has an immutable length and SHA-256 shared by every granted member.

For each initial or late grant, the coordinator starts the provisioned `gf-transfer receive` through the non-TTY exec WebSocket. It streams binary protocol chunks through stdin and reads durable acknowledgements from stdout; diagnostics stay on stderr. The helper stages and verifies the archive on disk, independently enforces archive confinement/type/expansion bounds, and extracts into `/workspace` before reporting completion. `member_ready` is conditional on the current lease generation. Extraction failures quarantine the member for reset; extraction itself does not resume midway.

Disconnected transfer attempts resume from the receiver's durable offset under the same transfer identity; retries and attempts share the session deadline and member-operation fencing. Whole-file `Filesystem.write` is used only to bootstrap a helper binary measured at most 16 MiB (16,777,216 bytes), the API's documented write limit. Workspace delivery does not use that endpoint. Initial goodci-to-GoodFlows HTTP uploads are unchanged. Writes per session remain sequential (the coordinator queues its members' hydrations and runs one at a time), and a node-wide transfer semaphore caps active transfers (default 2), serving queued report fetches before queued hydrations; memory scales with chunk size and concurrency, not archive size. Every workspace transfer attempt, retries included, first checks that the member is still leased to the session under the captured lease generation. Spools live under `<spool_dir>/<node>/<boot_id>/<session_id>`, so several nodes can share one `spool_dir` and the janitor only touches its own node's earlier boots. Delete the coordinator spool at session end.

### D6. Session liveness via a DB heartbeat, not presence

While joined, each channel process updates `pool_sessions.last_seen_at` every 15s, and immediately on join and terminate. The reconciler tick expires sessions where `now - last_seen_at > disconnect_grace_ms` (default 60s), `now - inserted_at > max_lifetime_ms`, or `first_granted_at IS NULL` and `acquire_deadline_at` has passed. Set `first_granted_at` atomically on the first grant and never clear it, even when all members are released. This works across nodes without Phoenix.Presence, and a node crash looks like a disconnect. In the worst case expiry fires about grace plus 15s late. The coordinator renews `owner_lease_expires_at` to now plus the grace; an unreachable owner counts as lost once that lease has expired (not a second grace later). Owners are probed concurrently in a tick. An owner id naming a node this VM has never seen (no atom exists for it yet, for example on a freshly booted node that has not joined the cluster) is unreachable, never confirmed lost: only a malformed id, or the owner's own node answering that it is not registered (or belongs to an earlier boot), is a confirmed loss. Creating-key validity for every open session is checked with one query per tick.

I merged the two clocks mentioned in exploration (a session TTL and a separate exec reconnect grace) into one disconnect grace. Execs live exactly as long as their session, which leaves one timer to reason about and one config knob.

### D7. ExecServer owns the command; channels only subscribe

An exec runs in an `ExecServer` GenServer under a `DynamicSupervisor` on the session coordinator's node, started through bounded owner RPC from the channel's node, so the captured credential never leaves the coordinator's node. It is registered in `Executions` with an owner id stored on the `pool_execs` row. The server calls a new `Sprites.spawn_streaming/…` (a bounded spawn that forwards `{:stdout|:stderr, data}` to the owner, with the same guard and kill semantics), stamps `seq`, keeps a ring buffer (default 1 MiB per exec), and broadcasts on PubSub topic `pool_exec:<id>`. The channel is not linked to it, so a socket drop doesn't affect the exec. `Sprites.spawn_streaming/…` and `Sprites.transfer/5` are non-blocking, unlike `bounded/3`, whose caller waits in `await/3` until the action ends: they start the SDK command in a `GoodFlows.Spry.TaskSupervisor` task (guarded and `Executions.track`ed like `bounded/3`), return `{:ok, handle}` immediately, and forward `{:stdout|:stderr|:exit, …}` to the owner, which enforces the hard deadline with a timer and cancels through `Executions.kill_and_confirm/3`, so the ExecServer and coordinator stay responsive to replay, cancel, and RPC calls. `SessionChannel` uses `use Phoenix.Channel, log_join: false, log_handle_in: false` so exec env values and commands are never logged at `:debug`. Coordinator and ExecServer state hold the credential only as a `%Sprites.Client{}` (or under a `:token` key) so `GoodFlows.Spry.Redaction` recognizes it, and both implement `format_status/1` to drop it from crash reports, and to redact a `{:start_exec, request}` last message (argv and env).

Each ExecServer monitors its session coordinator: when the coordinator stops for any reason (session end, lost lease renewal, crash), a running exec ends `error`/`owner_lost` and the server stops, so nothing runs on the credential after the session. Ending an exec (exit, timeout, cancel, stream failure, coordinator loss) runs off the server process in a task, so replay and cancel calls stay responsive: after anything but a normal exit, the remote process group is killed first and confirmed gone (the wrapper starts the command under `setsid` and records its process group id in `/tmp/gf-exec-<id>/pgid`; a bounded remote `kill -KILL -<pgid>` follows); then outputs and reports are collected (D8); then the exit is persisted and broadcast, and cancel callers are answered. When the remote process cannot be confirmed dead, the member is reset (`member_lost`), since only the checkpoint restore is sure to end it. Calls that cancel execs (`end_session`, `release_member`, `cancel`) use a timeout covering that whole stop. An ExecServer that fails to start after admission finalizes its row `error`/`exec_failed` and the request is answered `unavailable`.

On `exec`, the channel subscribes to the exec topic, replies with the exec id, and only then replays, so the reply always precedes the exec's output and exit. `replay` and `cancel` go straight to the exec's own ExecServer (by the `owner_id` on its row, through `OwnerRPC`), never through the session coordinator, whose lease renewal must not wait behind them. Crash reports of the coordinator and ExecServer also redact an upload chunk and exec output carried in the last message. WebSocket frames are capped at 1 MiB, an exec request at 4,096 argv items, 1,024 env entries, and 262,144 bytes of command/argv plus env, and `resume` at 1,000 entries.

**Resume:** the channel subscribes to the topic first, then calls the owner (`:erpc` to the owner node from the owner id) for buffered events after `last_seq`, and drops duplicates by `seq`. A `gap` is sent when `last_seq + 1` is older than the oldest buffered event. Buffer live messages while obtaining a replay high-water mark, emit replay in seq order, then flush newer buffered events, dropping duplicates. Persist the final output seq (initially -1) together with the terminal exit payload. After the ExecServer stops, stdout/stderr are unavailable: resume emits a gap for any missing range through that final seq before replaying the exit. Accept `last_seq = -1` when no output was received. Live output that skips seqs the channel never delivered is preceded by a `gap`, and so is an `exit` whose final output seq is past the last delivered seq (the internal exit event carries `final_output_seq`; the pushed payload does not); output after an `exit` is dropped, and resuming an exec the channel already tracks is a no-op. Execs listed in the join reply but not resumed still get their persisted `exit` before `session_ended`. The final `exit` event is persisted on the exec row (status, code, duration, reason, outputs bytes, report manifest), so `exit` can be replayed even after the ExecServer has stopped.

**Owner recovery:** use boot-aware `Executions` probes and conditional owner-fenced finalization. A failed RPC or missing cluster connection is not proof of death: keep the member unavailable until death/kill is confirmed or the recorded hard operation deadline plus recovery margin has elapsed, matching the existing Reaper fallback. Every spawn/read/hydration worker carries the lease generation and a hard deadline; losing its fence forbids further work or writes. Only then mark a lost exec `error` (`owner_lost`), persist/push its exit, and reset the member. The restore kills orphaned remote processes before reuse. Exec admission atomically reserves the member under the pool, session, and member row locks (in that order), and a database partial unique index enforces one running exec per member, including concurrent channel requests. Workspace completion also checks its captured session/lease generation, so a released or re-leased member cannot become ready from a stale upload.

### D8. Exec wrapper inside the member

The server builds the command line itself: it creates `GOODFLOWS_OUTPUT` (`mktemp`) and, if requested, `GOODFLOWS_REPORT_DIR` (`mktemp -d`) under `/tmp/gf-exec-<id>/`, then runs `sh -c <command>` or `argv` with `dir: /workspace/<cwd>` and the merged env, through `spawn`'s `:env` and `:dir` (never interpolated into a shell string). After every end (including timeout, cancel, and error, once the remote process is confirmed gone), one `gf-transfer collect` invocation returns, in a single bounded frame, at most 65,537 outputs bytes with a truncation flag (rejecting symlinks and nonregular files) and the report manifest of direct regular `*.jsonl` files (no-follow `lstat`, capped file count) whose names the helper can later send (`[A-Za-z0-9._-]{1,128}`); other names are counted as `reports.skipped`. A failed collect is flagged with `collect_failed` on the exit (persisted on the exec row), with `outputs` and `reports` both null, instead of passing for empty outputs or an empty manifest. It never goes through `exec/4`, whose UTF-8 tail trimming would corrupt binary outputs.

Report retrieval starts `gf-transfer send` for a server-authorized report. The helper creates a private immutable disk snapshot, enforcing regular-file/no-follow checks and the 32 MiB report cap, and supplies length and SHA-256. Its stdout streams chunks to the coordinator; stdin carries durable receiver acknowledgements. GoodFlows receives into a disk spool, resumes interrupted attempts against the same snapshot, and verifies the complete hash before serving HTTP. Report reads run on the coordinator; a request on another node streams the verified spool from the coordinator over bounded, acknowledged owner RPC chunks, as uploads do. Concurrent requests for the same report share one transfer. A request waits at most `report_fetch_timeout_ms`; timeout, semaphore saturation, or an internal transfer failure respond `503` with `Retry-After` while the report remains eligible. The route uses a pipeline without `accepts ["json"]` so `Accept: application/x-ndjson` is not refused with `406`. It never calls the SDK's whole-body `Filesystem.read/2`. Snapshot creation and transfer ownership serialize with next-exec admission/release; no new transfer starts after invalidation. All HTTP responses preserve the existing `404`/`410` boundaries. A finished transfer is rechecked for eligibility before waiters are answered, so a report released or superseded mid-transfer is `410`. Every `200` carries `x-content-sha256`; a cross-node stream invalidated after its headers were sent drops the connection instead of ending the chunked body, so a truncated download never looks like a complete `200`. A caller may retry its HTTP request and reuse an eligible completed spool; client HTTP Range resume is outside this change. The transfer semaphore bounds concurrency; deadline and generation fences bound every read. Before a report transfer starts, the coordinator reserves the 32 MiB report cap from the node spool budget and the account's share (`503` when it cannot), settles it to the verified size, and releases it when the report is invalidated or the session ends. SDK interactions stay exclusively in `GoodFlows.Spry.Sprites`.

### D9. Socket authentication through the Phoenix auth token

`socket "/api/v1/socket", GoodFlowsWeb.PoolSocket, auth_token: true, websocket: [connect_info: [:auth_token]], longpoll: false`. `connect/3` verifies the token with `Accounts.verify_api_token/1`, requires `ApiKey.can_write?/1`, and refuses any `params["token"]`. The Phoenix 1.8 auth token travels in `Sec-WebSocket-Protocol`, so it never appears in request-line logs. Key revocation is checked on join and on every heartbeat write, which expires the session with `key_revoked`. The Rust client must send both `phoenix` and `base64url.bearer.phx.<base64url-token>` subprotocols. The top-level `auth_token: true` enables header extraction; connect_info alone is insufficient. Verify header extraction with a real WebSocket handshake, since ChannelTest bypasses the transport. This is verified first, in task 1.1.

**Spike result (task 1.1, 2026-11-01): passed.** A throwaway Rust client (pinned `phoenix-channel-client`/`phoenix-channel-runtime-native` `=0.1.1`) was run against the real endpoint served by Bandit on loopback, driven from `GoodFlowsWeb.PoolSocketTest`. The spike code and its opt-in test were deleted after the run; this record is the result, and `PoolSocketTest` keeps the real-handshake subprotocol and refusal tests. Observed:

- `ConnectionConfig::auth_token(sk)` sends `Sec-WebSocket-Protocol: phoenix, base64url.bearer.phx.<token>`, where `<token>` is **standard** base64 without padding (not the URL-safe alphabet, despite the prefix name). Phoenix decodes it with `Base.decode64(padding: false)`, so any other client must use the same encoding. The server selects `phoenix`, never the token protocol. The client appends `/websocket?vsn=2.0.0` itself.
- Join, a server push (`member_granted`), a client-side `disconnect()`, `connect()` again, the runtime's automatic rejoin, and a push after the rejoin all succeeded.
- The runtime's per-event subscription also yields lifecycle events (`Disconnected`) that the goodci transport must skip.
- A `?token=` query parameter, a `pk_` key, and a missing token are refused with `403` before upgrade, and no log line at `:debug` contains the key (the socket uses `log: false`).

### D10. Data model

- `pools`: project_id (composite `(project_id, account_id)` FK, `on_delete: :nothing`, like recipes and test_reports, mapped by `no_assoc_constraint(:pools, name: :pools_project_id_fkey)` in `Project.delete_changeset/1` to `{:error, :has_pools}` and a `409`), account_id, slug, setup (`text[]`), min_ready, max_members, setup_version, deleting_at, provision_failures, next_provision_at, last_provision_error, idle_ttl_ms (nullable; opt-in idle shrink).
- `pool_members`: pool_id (`on_delete: :nothing`; the reconciler deletes members before the pool row), credential_fingerprint, credential_snapshot (encrypted/redacted, never serialized), pool_id, name (unique), state, setup_version, helper_version (packaged artifact SHA-256 and protocol version), golden_checkpoint_id, session_id (nullable), lease_generation, workspace_ready_generation (the member is ready when it equals lease_generation; set by a lease-generation-fenced update), owner_id, operation_deadline_at, last_error, failures, next_attempt_at, idle_since (set whenever the member becomes idle).
- `pool_sessions`: credential_fingerprint (internal), owner_id, owner_lease_expires_at, pool_id, account_id, pool_id (`on_delete: :nilify_all`), pool_slug and project_slug (copied at creation so history survives pool deletion), api_key_id (nullable, `on_delete: :nilify_all`; the reconciler tick expires any nonterminal session whose `api_key_id` is NULL or whose key is revoked or expired with `key_revoked`, before the disconnect-grace check), status, end_reason, max_members, wanted, granted_count, wanting_since, label, acquire_deadline_at, first_granted_at, workspace_uploaded_at, last_seen_at, ended_at.
- `pool_execs`: session_id (`on_delete: :delete_all`), member_id (`on_delete: :nilify_all`), member_name (copied at creation), job, step, status, exit_code, outputs (bytea ≤ 65,537), outputs_truncated, reports (jsonb manifest), owner_id, operation_deadline_at, final_output_seq, error_reason, duration_ms, started_at, ended_at, bytes_stdout, bytes_stderr.

Every `account_id` FK uses `on_delete: :delete_all`, as on existing tables. Member names are `gfp-` plus 16 random lowercase base32 characters, checked by a unique index with bounded retry on collision. CHECK constraints pin member states, session statuses and end reasons, and exec statuses, and the invariants `0 <= min_ready <= max_members`, `max_members >= 1`, `idle_ttl_ms > 0`, `granted_count >= 0`, and `0 <= wanted <= max_members`. `pool_sessions.api_key_id` (nilified on key delete) and `ended_at` (retention) are indexed, and `pool_execs (member_id, started_at, id)` serves the latest-exec lookup.

### D11. Reserved prefix

`Template` gains `reserved_sprite_name?/1` (literal `gfp-` prefix). `Recipe.name_format_errors/2` rejects a literal `gfp-` name on `name`, `Plan.sprite_override_errors/2` rejects an override on `sprite`, and `Plan.expand_name/2` rejects an expanded `gfp-` name on `sprite_name`. Pool members are created only by the reconciler, so the existing one-active-run-per-sprite guard never sees a member name.

### D12. Rust helper and resumable binary protocol

The approved detailed protocol is in [transfer-design.md](transfer-design.md), with normative behavior in `specs/sprite-transfers/spec.md` and implementation steps in `implementation-plan.md`. The `sprite-transfer/` crate builds `gf-transfer`, a short-lived CLI inside the Sprite with `receive`, `send`, `collect` (bounded outputs read and report manifest, no resume), and a version handshake. Install an architecture-matching release binary, verify its checksum/version after setup, and then take the golden checkpoint. No HTTP listener or Sprites credential is required inside the VM.

Protocol v1 frames contain a 4-byte big-endian JSON-header length (at most 8 KiB), that header, and its declared raw payload (at most the negotiated 1 MiB default chunk). Decode across arbitrary stdin/stdout/WebSocket fragmentation. One chunk is in flight initially; the receiver validates SHA-256 and the exact expected offset, syncs file data, atomically persists/syncs its sidecar, then acknowledges. Open/reopen returns the authoritative committed offset. Transfer identity binds the direction, session/member/lease generation, artifact, length, and whole-file hash; mismatches are refused. The sender supplies length/hash before the receiver binds a new transfer: uploads send metadata in open; downloads first request a snapshot by identity, the helper offers its fixed length/hash, and the receiver answers with its durable offset before chunks begin. Reopens must match the bound metadata. Finish verifies the whole file and publishes idempotently. A checksum mismatch cannot publish data.

Upload partials and download snapshots live in private on-Sprite transfer directories outside `/workspace`; download receiver state lives in the coordinator spool. Locks and fenced owner termination prevent competing attempts. Reconnect neither resets a member nor discards valid partials, but release/reset, session expiry, next exec for reports, or coordinator loss invalidates them. Explicit cleanup and checkpoint restore precede member reuse. The live transport spike must prove >16 MiB bidirectional binary transfer, backpressure, EOF, disconnect/restart resume, and complete integrity before production integration. The API's per-write maximum is not a claim about unlimited WebSocket transfers.

Provisioning runs `uname -m` and maps it to a packaged static musl target (`x86_64` → `x86_64-unknown-linux-musl`, `aarch64` → `aarch64-unknown-linux-musl`); an unmapped value fails with `unsupported_architecture`. Each invocation holds an OS advisory lock (`flock`) on its transfer state, released on process exit, and exits on stdin EOF, after `--idle-timeout-ms` without frames, and at `--deadline-unix-ms` (the lease/session deadline), so a stale remote helper cannot hold a transfer indefinitely; a replacement that finds the lock held may wait up to the idle timeout before reporting `busy`. The sender proposes a payload maximum in `open` and the receiver answers in `ready` with the lesser of that and its own (default and ceiling 1 MiB); the 8 KiB header limit is fixed. `Sprites.transfer/5` spawns with `stdin: true` and `tty: false`, routes `{:stderr, …}` messages only to the scrubbed diagnostics path and never into the protocol decoder (`stderr_to_stdout` is a `Sprites.cmd/4` option, not a `spawn/4` one), treats a successful stdin write as queued rather than delivered (backpressure comes only from protocol acks), and splits stdin writes into WebSocket sub-frames of at most 64 KiB, independent of the protocol chunk size. The spike records whether 1 MiB single frames are accepted. A helper watchdog also enforces the idle timeout and deadline while the helper is blocked writing stdout (exit status 3, retried by the server). The server binds `--deadline-unix-ms`, the stream timeout, and permit waits to the session's real expiry and starts no attempt after it; waits for an attempt's first frame for the helper idle timeout plus the ack timeout (a replacement may wait that long for the lock); retries `busy`; sends EOF synchronously and waits briefly for the helper to exit before stopping a stream; requires every frame to carry the attempt's `transfer_id`; refuses spooled download progress bound to other metadata (`metadata_mismatch`, discarded); budgets helper stdout per attempt and caps forwarded stderr. Details are in transfer-design.md, "Hardening".

Do not archive this change until the spike has run and its results are recorded here. `sprite-transfer/examples/transport-spike.exs` drives the production `GoodFlows.Pools.Transfers` path against a throwaway Sprite (>16 MiB random payloads both ways, an interrupted first attempt, resume, SHA-256 comparison). ### D13. Configuration, rollback, and shutdown

`GoodFlows.Pools.Config` holds every pool setting and validates it at boot. Initial defaults, all overridable: per-pool member cap 32; provision budget (`provision_timeout_ms`) 30 min, with startup validation that the provision job timeout covers that budget plus checkpoint and helper-install margin, and a member exceeding it becomes `broken` with a timeout error; workspace compressed 256 MiB, expanded 2 GiB, 100,000 entries, archive validation deadline 60 s, helper extraction budget (`helper_extract_timeout_ms`) 300 s, upload read deadline 300 s, per-account concurrent uploads 1 (per node); transfer chunk 1 MiB (ceiling), transfer concurrency 2, ack timeout 30 s, 5 attempts with exponential backoff inside the session deadline, helper idle timeout 60 s; report fetch wait 60 s, report files 100; `spool_dir` `goodflows-pools` under `System.tmp_dir!/0`, `spool_max_bytes` 2 GiB; `spool_account_max_bytes` 1 GiB; disconnect grace 60 s, max session lifetime 6 h, acquire timeout max 10 min; exec max 1 h, exec buffer 1 MiB; ended-session retention (`session_retention_ms`) 30 days. Credential fingerprints are keyed with `fingerprint_secret` (production: `POOL_FINGERPRINT_SECRET`, falling back to `SECRET_KEY_BASE`), so the pools core does not read the web endpoint's config and the web secret can rotate without rebuilding every pool. The transfer tuning, helper idle timeout, report settings, and interval settings are config-only (no environment variable).

`enabled` (env `POOLS_ENABLED`, default true) is read through `Pools.Config.enabled?/0`. When false, `PoolSocket.connect/3` refuses, a router plug on the pool (except pool deletion), session, workspace, and report routes responds `503`, and no member is granted, provisioned, or retired as stale. So that a rollback can be cleaned up, the reconciler still expires sessions, recovers and resets members, destroys broken members, and completes pool deletions, and the reset and destroy jobs still run (with member snapshots). A node with pools disabled leads the reconciler only for one pass at a time and then frees the leader name, so an enabled node takes over. The endpoint `socket` declaration is compile-time, so the flag is checked at runtime instead of removing the route.

`sprite-transfer/scripts/package.sh` builds static musl binaries for each supported target into `app/priv/gf-transfer/<target>/gf-transfer` with a `manifest.json` (version, protocol, SHA-256, size, target). The directory is gitignored and packaging runs before `mix release`. `Pools.Config` reads `:helper_artifact_dir` (default `priv/gf-transfer` in the app dir); when the manifest is missing or invalid, a production node with pools enabled refuses to boot (`require_helper_manifest`, set in `config/runtime.exs` for prod; the packaging step is documented in `app/README.md`), while dev and test log an error and disable pools. There is no CI or Dockerfile to wire packaging into. `mix precommit` builds the helper's debug binary (`cargo build`) so the `:helper_binary` tests run, but not the crate's own checks, which are run explicitly (task 9.2). A config test fails when the local helper's version handshake does not match `Cargo.toml` (a stale build). A plain `mix test` without the helper skips those tests with a warning, and fails when `CI` is set. The manifest also records `rustc` (the build's `rustc -V`); readers ignore it. `app/.sobelow-conf` now sets `skip: true`, so the `# sobelow_skip` annotations take effect; each one marks a path built only from server-side values (spool root, boot id, UUIDs, hashed report names), never from request data. `config/test.exs` sets `:helper_artifact_dir` to `test/support/fixtures/gf-transfer`, which holds a committed fixture `manifest.json` and stub binaries per supported target, so pools are enabled in tests without cargo.

`GoodFlows.Application.prep_stop/1` stops pool admission before any child stops. `Pools.ShutdownDrain`, then the session coordinator and ExecServer supervisors and the transfer semaphore, start in the main child list after `Phoenix.PubSub` and before `GoodFlowsWeb.Endpoint` (so channels stop first), not in `pgflow_children/1`, which is empty in tests; only `PoolReconciler` goes there next to `ReaperScheduler`. `Pools.Config.validate!/0` runs in `Application.start/2` after `SpryConfig.validate!()`. The drain, like `GoodFlows.Spry.ShutdownDrain`, stops admission on a draining node, ends its local sessions with `session_owner_lost`, persists `error`/`owner_lost` exits, and deletes spools, so clients fail fast instead of waiting out the grace period.

## Risks / Trade-offs

- [`phoenix-channel-runtime` is v0.1, single maintainer] → The contract is plain Phoenix Channels v2, so any compliant client works. The goodci side hides it behind a transport trait and pins the version. Task 1.1 spikes the auth token, reconnect, and rejoin against this server before anything else is built.
- [Credential replacement changes the remote namespace] → Tag members and sessions with an internal credential fingerprint: HMAC-SHA256 of the token keyed with a server secret (`fingerprint_secret`, see D13; never a bare hash). `SpritesCredential` stores no organization identity, so any token replacement, even within the same Sprites organization, is a new namespace that rebuilds members; org-preserving rotation is deferred to a later change. A session is granted only matching members. Members retain an encrypted, redacted creation-credential snapshot using `GoodFlows.Encrypted.Binary` and query logging disabled, solely for reset/destruction; never attempt cleanup with a different token and only treat `not_found` under the original credential as cleanup success. Replacement stops old-generation warm provisioning; preserve existing matching members for old sessions and retire them once no such session needs them. New provisioning uses the current credential. Revoked creation credentials may make cleanup impossible: retain the member and sanitized retry diagnostics rather than silently dropping a remote VM. Missing account credentials pause only provisioning; reset and destruction of existing members continue with their creation-credential snapshots. Internal fingerprints and snapshots are never exposed.
- [A setup that installs a toolchain takes minutes] → `min_ready` hides it for steady traffic. Bursts beyond warm capacity wait for provisioning, bounded by the client's `acquire_timeout_ms`.
- [Memory pressure from large workspaces] → Disk spooling, bounded 1 MiB protocol chunks, sequential per-session writes, and a node-wide transfer semaphore (D5/D12).
- [Exec output is lost on owner-node death] → The exit is still persisted as `error` (`owner_lost`). The client sees a failed job, not a hang.
- [Remote shell keeps running after a local kill] → Same as runs (documented in `Sprites`). Member reset restores the checkpoint, which ends all processes before reuse.
- [Deploys end sessions owned by restarted nodes] → `Pools.ShutdownDrain` (D13) ends them promptly with `session_owner_lost` so clients fail fast and can retry; release notes call this out.
- [Late expiry up to grace + tick interval] → Acceptable for leak prevention. Explicit release on client exit is the fast path.
- [Warm members cost money while idle] → `min_ready` is the floor the operator chose; pools that should shrink back after bursts opt into `idle_ttl_ms`.
- [Revoked creation credential] → Destruction cannot succeed; the member becomes `abandoned` after repeated authorization failures and is logged by name when forgotten, so an operator can remove the sprite in Sprites.
- [Breaking: recipes named `gfp-…`] → Before deploying, check for existing recipe names with a literal `gfp-` prefix. The app is pre-1.0 and none are expected. Existing ones fail with `422` on their next run request (the expanded-name check runs on every run) and on their next save, which release notes call out.

## Migration Plan

Additive migrations (four new tables), plus a versioned helper release artifact. There is no data backfill. Deploy order is helper artifact and compatible server first, then the goodci release. Existing golden checkpoints without the required helper are rebuilt before use. Rollback: set `POOLS_ENABLED=false` (D13), and leave the tables in place; sessions still expire, members are still reset and destroyed, and pools can still be deleted (`DELETE` stays available). Members of abandoned pools can also be destroyed with a `mix pools.destroy_members POOL_ID` task added in tasks.
