# Proposal

## Why

Goodflows needs a durable destination for test reports generated by local and CI runs. GoodFlows already provides account-scoped API authentication, account-owned projects, and Postgres, but its existing run endpoints manage Spry executions rather than externally collected test results.

## What Changes

- Add a private-key-authenticated `POST /api/v1/projects/:project/test-reports` endpoint. The path slug selects the project the same way nested recipe routes do. The JSON body does not carry `project`.
- Store validated test reports with account, project, workflow invocation, job, suite and report identities, execution context and per-report completion status. The path slug must name an existing project of the authenticated account. The report row stores that project's id. An invalid slug is `422` on `project`. A slug the account does not have, including one that exists only on another account, is `404`. Either case stores nothing. A body key `project` is an unknown field and is `422`. The stored document is the validated body.
- Make exact retries idempotent and conflicting reuse of an identity a conflict, including concurrent requests.
- Store failed and partial reports without treating them as successful complete runs.
- Define a bounded, explicit payload contract that excludes logs, arbitrary metadata values, credentials and failure payloads.
- Bound each upload's cost: body size, nesting depth, record count, an overall read deadline, per-node and per-account concurrency caps held through persistence, and a request heap limit. A per-account storage quota is deferred (accepted risk).
- Provide acknowledgement responses only. Dashboards, query APIs, grouping, scheduling, generic artifact storage and changes to Spry runs are outside this change.

## Capabilities

### New Capabilities

- `test-report-storage`: authenticated ingestion, report validation, account-scoped immutable storage and idempotency.

### Modified Capabilities

- `projects`: extend deletion protection to stored test reports, preserving recipe protection. Apply and sync/archive `scope-recipes-by-project` first so its new `projects` capability exists before this change's MODIFIED delta is synced.

## Impact

- Add a test report context/schema, migration, controller, OpenAPI request/response schemas, endpoint-specific body handling, fixtures and context/controller tests.
- Reuse `GoodFlowsWeb.Plugs.ApiAuth` and `GoodFlowsWeb.Plugs.LoadProject` on the nested write pipeline `[:api, :api_authenticated, :api_write, :load_project]`. No new credential type or background worker is needed.
- Depend on the `projects` table, `GoodFlows.Projects`, and `LoadProject` from `scope-recipes-by-project`. Apply that change first. This change does not create projects and does not alter the `projects` table. It adds `has_many :test_reports` on `Project` and extends deletion: a project with a test report returns `409` and keeps the report, including when it has no recipes. The foreign key is a composite `(project_id, account_id)` key with `ON DELETE NO ACTION`, matching `recipes.project_id`.
- Companion publisher: `../goodci/openspec/changes/upload-test-timings/`.
- Companion producer: `../goodcases/openspec/changes/publish-test-timings/`.
- This change owns the shared wire contract and server implementation; the companion changes own their repository-local implementation. Companions must post to `/api/v1/projects/:project/test-reports` and omit `project` from the JSON body. `goodci` still targets `/api/v1/test-timing-reports` and puts the project in the body; update that change before implementation is ready.
