# Design

## Context

See proposal.md for motivation. The app has Postgres, account-bearing API keys, OpenAPI and an existing `:api_write` scope. `GoodFlows.Spry.Run` represents VM lifecycle execution and must not become the test-report table. The endpoint currently uses a general JSON parser; report uploads need their own body limit. No background processing or outbound request is necessary.

## Goals / Non-Goals

**Goals:** A small synchronous, immutable ingestion boundary with enough execution context to support later timing analysis. Preserve measured versus observed timings and report completeness.

**Non-Goals:** Normalized rows for every test event, timing queries, UI, partition recommendations, retention automation, live streaming and generic file storage.

## Decisions

### D1. Authoritative wire contract

This section is the shared contract for the companion changes in `goodci` and `goodcases`. Changes to it must be reflected in both companions before implementation is considered ready. Use `POST /api/v1/projects/:project/test-reports`, `Content-Type: application/json`, `Authorization: Bearer <private-key>`, with one report per request. The path slug is the project. The body does not carry it:

```json
{
  "format": "exunit-timings",
  "workflow_run_id": "67f7946d-136b-4608-ab01-e1f251a09754",
  "workflow": "default",
  "environment": "local",
  "job": "test",
  "job_status": "passed",
  "source": {"commit": null, "branch": null, "dirty": null},
  "report": {
    "suite_id": "suite-123",
    "report_id": "report-1",
    "partition": "1",
    "partition_count": 3,
    "truncated": false,
    "records": []
  }
}
```

The example shows the envelope shape; a valid `records` array is nonempty and starts with `suite_started`. There is no client-supplied account id. Required keys are exactly those shown; environment is null or a nonempty string of at most 64 UTF-8 bytes with no control characters, matching the publisher's environment-name rule. Source is a required object whose three values can be null. All string length limits in this contract are measured in UTF-8 bytes, and no string at any level may contain U+0000 (Postgres JSONB rejects it); such documents are 422. `workflow_run_id` is a lowercase canonical UUID string generated by the CLI; other spellings are 422. The path `:project` is the same 1-64 byte slug as `GoodFlows.Projects.Project` (`[a-z0-9][a-z0-9_-]*`), checked with `Project.valid_slug?/1`. `LoadProject` assigns that account's `%Project{}`. The row stores `project_id` from that struct. An invalid slug is 422 on `project` and does not query. A slug the account does not have, including another account's slug, is 404. A body key `project` is an unknown field (422). The stored payload is the validated body and does not gain a slug. This depends on `scope-recipes-by-project`; apply that change first so `projects`, `GoodFlows.Projects`, and `LoadProject` exist. Workflow/job names are nonempty, at most 64 bytes and contain no control characters. Job status is `passed`, `failed`, `timed_out`, `cancelled`, `skipped` or `unknown`; publishers MUST map every job result to exactly one of these values, using `unknown` when no mapping applies. Source contains only commit (40/64 hex characters or null), branch (a nonempty string of at most 256 bytes, or null; `""` is 422, so publishers send null when there is no branch) and dirty (boolean or null); repository URLs and arbitrary environment metadata are not accepted.

Suite/report ids are 1-128 bytes matching `[A-Za-z0-9][A-Za-z0-9._-]*`. `report_id` MUST be unique within a workflow job across all suites (the identity key in D2 does not include `suite_id`). Partition is null or a JSON string of 1-64 bytes matching `[A-Za-z0-9._-]+`, in both the envelope and `suite_started`; producers normalize an empty partition value to null. Partition count is null or a positive integer. Envelope partition and partition_count must equal the initial suite-started values. `truncated` records whether collection discarded an invalid final JSONL fragment; it never claims the original file was repaired.

Identifier glossary: `suite_id` is the producer suite identity, carried in each event as `run_id`; `workflow_run_id` is the goodci invocation UUID; neither relates to Spry `runs`.

Every event includes `event`, `run_id`, `report_id` and nonnegative integer `received_offset_us`. Event `run_id` must equal envelope `suite_id`, and event `report_id` must match its envelope. The CLI workflow identity does not replace the producer suite identity. Allowed event-specific keys are:

| Event | Additional fields |
| --- | --- |
| `suite_started` | `format` (exactly `exunit-timings`), UTC `started_at`, nullable `partition`, nullable positive `partition_count`, nullable integer `seed`, positive `max_cases` and `schedulers`, `elixir_version`, `otp_release`, `filters` |
| `test_started` | `module`, `name`, nullable `description`, nullable relative `file`, nullable positive `line`, nullable `describe`, nullable boolean `async`, nullable positive integer `parameter_id`, positive integer `execution_id`, nonnegative `started_offset_us` |
| `test_finished` | All test-started fields plus `duration_us` and `outcome` |
| `module_started` | `module`, nullable relative `file`, nullable boolean `async`, nullable positive `parameter_id`, positive `execution_id`, nonnegative `started_offset_us`, boolean `setup_all` |
| `module_finished` | All module-started fields plus nullable nonnegative `observed_duration_us`, `outcome`, `counts` |
| `suite_finished` | boolean `aborted`, nonnegative `unfinished_tests` and `unfinished_modules`, `counts`, `files`, `times_us` |
| `max_failures_reached`, `interrupted` | No additional fields |

Test outcomes are `passed`, `failed`, `skipped`, `excluded`, `invalid`; module outcomes use the same vocabulary. `duration_us` is nonnegative for executed passed/failed tests, null for other outcomes. Module counts retain ExUnit's module-finished semantics, which can omit excluded/skipped tests. Description is null on installed ExUnit versions without that field. Unknown parameterizations retain null; parameter values are never transported.

`counts` is an object whose keys are only the five outcomes and whose values are nonnegative integers. `times_us` has exactly `run`, `async`, `sync`, `load`, `total`; async/load can be null and others are nonnegative integers. Its sync/total values follow `run - (async || 0)` and `run + (load || 0)`.

Each `files` element has nullable relative `file`, `test_count`, `module_count`, `counts`, `test_duration_us`, `observed_module_duration_us`, and `async`, `sync`, `unknown` subobjects. Each subobject contains those cost/count fields without file or nested buckets. All numeric costs/counts are nonnegative integers. Nested objects have no freeform extension keys. Files must not be absolute or contain parent traversal; missing source locations remain null.

`filters` contains only `include` and `exclude` arrays of `{tag, value}` objects. Tag is one of `chrome`, `goodaudit_integration`, `athena_preview`, `chromic_teardown`, `qpdf`; value is boolean. `module`, `name`, `description` and `describe` are at most 4,096 bytes; `file` is at most 4,096 bytes; `elixir_version` and `otp_release` are at most 128 bytes. These fields do not authorize logs, stacktraces, assertion data or arbitrary tags.

Require a single initial suite-started event and at most one suite-finished event, last if present. Validate required fields/types, matching identities, execution start/finish identity consistency and terminal event ordering, while allowing unmatched starts in incomplete reports. Do not require measured test duration to fit event receipt intervals: formatter queue latency makes that inference invalid. Preserve documents after validation; do not infer per-test timings from offsets or rewrite supplied durations. Final summary counts/file totals must agree with finished events and bucket sums using the formatter's documented aggregation rules; module-finished `counts` are stored but not cross-checked, because ExUnit can omit excluded/skipped tests from them.

Maximum body is 32 MiB (33,554,432 bytes; exceeding it is 413), maximum records 100,000 (exceeding it is 422 on `report.records`, a structural limit checked after decoding). The top-level body must be a JSON object. Integers are JSON numbers without fraction or exponent and at most 2^53-1. Duplicate object keys are invalid (decode this route with `Jason.decode(body, objects: :ordered_objects)` to detect them). Unknown fields at any level are invalid, including any client-supplied `account_id` or `project`; query parameters are ignored. Objects and arrays nest at most 16 levels deep (the deepest contract structure, `body → report → records → suite_finished → files → file → bucket → counts`, is 8); a deeper body is 422 on `body` (`is nested too deeply`), found by a byte scan that tracks bracket depth outside strings before decoding, so a pathological body is never decoded. The path slug is not a body field, so it never trips the unknown-field rule. There is one active format, with no legacy compatibility parser.

### D2. One immutable report row

Add `GoodFlows.TestReports` and a `Report` schema backed by `test_reports`: UUID id, account id foreign key, `project_id` foreign key, workflow_run_id UUID, workflow, nullable environment, job, job_status, suite_id, report_id, nullable partition and partition_count (`bigint`, since validated integers reach 2^53-1), derived status (`complete` or `incomplete`), immutable `payload` JSONB, `payload_digest` (the SHA-256 of the payload's canonical JSON, see D3), and inserted timestamp. Use `account_id references(:accounts, type: :binary_id, on_delete: :delete_all)` to match existing tables, `project_id` as a composite foreign key `(project_id, account_id)` referencing `projects (id, account_id)` with `ON DELETE NO ACTION` (the same shape as `recipes.project_id`, so a report's account always matches its project's, and an account delete cascading to both projects and reports succeeds in any cascade order; `RESTRICT` would check immediately and could fail that cascade), `api_key_id references(:api_keys, type: :binary_id, on_delete: :nilify_all)` to record submitting-key provenance, and `timestamps(type: :utc_datetime_usec, updated_at: false)`. Payload is the validated body, including all records and source context, and not a project slug. Index `(account_id, project_id, inserted_at)` and `api_key_id` (for the nilify on key delete), and uniquely constrain `(account_id, project_id, workflow_run_id, job, report_id)`. No separate `project_id` index: both of the other indexes lead with `(account_id, project_id)`, which serves the composite foreign key's delete check. Add `has_many :test_reports, GoodFlows.TestReports.Report` on `Project`. Extend `Project.delete_changeset/1` with `no_assoc_constraint(:test_reports, name: :test_reports_project_id_fkey)`. `Projects.delete_project/2` already maps a `:recipes` constraint error to `{:error, :has_recipes}`. A `:test_reports` constraint error MUST return `{:error, :has_test_reports}`, not `:not_found`. `FallbackController` renders that atom as 409 with a fixed detail that does not include ids or the payload, beside the existing `:has_recipes` clause. A project with reports and no recipes still returns 409 and keeps both rows. A project deleted after `LoadProject` ran makes `insert_all` hit the foreign key; rescue only a violation of `test_reports_project_id_fkey` into 404 and store nothing. Any other foreign key violation (the submitting API key deleted between authentication and insert, or the account) is rescued into `{:error, :test_report_storage_unavailable}` and rendered as 503 with `Retry-After`; nothing is stored and a retry fails authentication cleanly. Do not create the `projects` table, edit its migration, or change its columns.

JSONB keeps ingestion/storage small in scope and preserves all timings for later analysis. Per-test tables and materialized historical statistics would create query-oriented obligations before a query product is requested. No parent run table is needed: this API does not claim whole-invocation completion. Do not add a foreign key to Spry's `runs`.

### D3. Atomic idempotency

Use `Repo.insert_all(Report, [row], on_conflict: :nothing, conflict_target: [:account_id, :project_id, :workflow_run_id, :job, :report_id], returning: [:id, :status])` (through the thin `GoodFlows.TestReports.Store` wrapper, which tests stub instead of copying `Repo` suite-wide): one returned row is a 201; zero rows means the insert lost, so run an account-scoped lookup that compares digests in SQL (`select: {r.id, r.status, r.payload_digest == ^digest}`). The row stores `payload_digest`, the SHA-256 of the validated payload's canonical JSON (object keys sorted by UTF-8 bytes, no whitespace, strings and integers as Jason encodes them), so a retry sends the payload once (with the insert) and only 32 bytes for the comparison; a single-statement CTE was rejected because its select cannot see a row committed concurrently during the statement, which would need a second query anyway. Do not rely on `Repo.insert(on_conflict: :nothing)`, which returns a client-generated id that was never persisted, and do not load the stored payload into the BEAM for comparison. Comparison covers the entire validated envelope (including `job_status`, `environment`, `source` and `truncated`): object key ordering does not matter at any level; arrays compare by order; strings compare exactly with no normalization; numbers are integers after validation and compare by value. Equal payload returns 200, any difference returns 409. The inserted document never changes, including incomplete documents: later complete bytes under the same identity are a conflict, not an update. Publishers must wait until local writers are done and retry frozen snapshots.

201/200 body is `{"data":{"id":"<server-uuid>","report_id":"report-1","status":"complete","duplicate":false}}`; exact retries set duplicate true and retain the same server id. Reuse existing error response conventions: 422 bodies use `ValidationErrorResponse` (`{"errors":{"<json path>":["<message>"]}}`, keys such as `report.records[3].duration_us`, values from a closed list of fixed messages that never interpolate submitted values; an unknown or duplicate key is reported on its enclosing object as `has an unknown field` / `has a duplicate key`, so submitted key names are never echoed (a body `project` is `{"body": ["has an unknown field"]}`); at most the first 50 errors, in document order, are returned); 400/409/413/415/503 use `ErrorResponse` (`{"errors":{"detail":"..."}}`). 409 detail is a fixed conflict message and never includes the stored id or payload. Connection errors, timeouts and other transient database errors during the persistence step (insert or compare: `DBConnection.ConnectionError`, SQLSTATE classes 08, 40, 53 and 57, `55P03` lock_not_available and `25006` read_only_sql_transaction), and foreign key violations other than the project's, are rescued into `{:error, :test_report_storage_unavailable}` and rendered by the FallbackController as 503 with `Retry-After`. Both queries run with an explicit `timeout:` from `:test_report_db_timeout_ms` (default 15,000). Any other Postgres error is logged with only its SQLSTATE and constraint name and re-raised as `GoodFlows.TestReports.StorageError` with a fixed message (a 500), never with the Postgres message or detail, which can quote submitted values. Validation errors are `{:error, {:invalid_test_report, errors}}`, so the shared fallback clauses are named for this context; DB failure during `ApiAuth` keeps the existing 500 behavior. Never acknowledge before commit. A connection failure or timeout can leave the commit outcome unknown: 503 does not guarantee the row is absent. Publishers retry the same frozen payload and identity to discover the committed row or insert it once; the server never guesses success after losing commit confirmation. Auth is evaluated on retries too, so revoked keys cannot probe existing documents.

### D4. Per-report completion

Derive complete only from a final suite-finished event with aborted false, both unfinished counters zero, no interruption/max-failures marker, and truncated false. Failed test counts or failed job status do not imply incomplete. Absence of a final marker or a positive unfinished counter yields incomplete. Partition count is retained for future consumers, but no aggregate run completion or statistics are computed.

### D5. Endpoint isolation

Add the route on the nested write pipeline recipe writes use, `[:api, :api_authenticated, :api_write, :load_project]`:

```
POST /api/v1/projects/:project/test-reports
```

Authenticate and resolve the project before reading the body. `:api_write` runs before `:load_project`, so a public key is 403 before slug validation, matching recipe writes. Wrap the existing `Plug.Parsers` in a `GoodFlowsWeb.Plugs.BodyParsers` plug that leaves a path of the shape `["api","v1","projects",_project,"test-reports"]` unread and applies the current parser options unchanged to every other path. After `LoadProject` assigns the project, a route-local report body plug checks Content-Type (`application/json`, optionally `charset=utf-8`) and Content-Encoding (absent or `identity`) and returns 415 otherwise. It rejects a declared Content-Length over the limit with 413 without reading, then reads in `read_body` chunks of at most 1 MiB against one monotonic overall deadline (`:test_report_read_timeout_ms`, default 60,000; each read's `read_timeout` is the time left), returning 408 once the deadline passes and 413 as soon as the bytes read exceed the limit, whatever the adapter's return tag (`{:ok, …}` or `{:more, …}`). The adapter length option is approximate; its return tag alone does not enforce the exact byte boundary. Streamed or understated-length oversize bodies also return 413. A slow client therefore holds a slot for at most the deadline. Before decoding, the depth scan of D1 rejects nesting deeper than 16 levels with 422 on `body`. Unauthenticated requests get 401/403 without their body being read. Invalid and missing projects get 422/404 without their body being read. The plug rescues parser and `Jason.DecodeError` exceptions and renders `ErrorJSON` bodies with no exception data, whatever the Accept header. Admission (`GoodFlowsWeb.TestReportAdmission`) covers the whole upload after authentication: body reads, the depth scan and decode, validation and persistence. The plug acquires a slot before reading and returns 503 with `Retry-After` without reading or writing when either cap is reached: a per-node cap (`:test_report_max_concurrent_uploads`, default 2) and a per-account cap (`:test_report_max_concurrent_uploads_per_account`, default 1, holders keyed by account), so one account cannot take every slot. The slot is stashed in `conn.private`; the plug releases it on any rejection, and the controller releases it in a `try … after` around `ingest/4`, so it is released on success, parser/validation/storage errors and exceptions; a monitor also releases it when the request process exits. An acquire that cannot be answered within one second returns `:full` (503), and a request reaching the server after its deadline is refused rather than granted; release is a cast. Each admitted upload holds at most one `Repo` connection at a time (insert, then compare, outside a transaction), so the node cap must stay well below the Repo `pool_size` (default 10): in production `config/runtime.exs` refuses to boot unless the cap is at most half of `POOL_SIZE`, leaving connections for authentication and other traffic, which resolves pool starvation by uploads. While it holds a slot, the request process runs with `Process.flag(:max_heap_size, …)` (`:test_report_max_heap_bytes`, default 2 GiB, restored on release) as a backstop: a body that would exhaust memory kills its own request process instead of the node. A real 100,000-record report just under 32 MiB peaks at under 1 GiB of heap through decode, validation and digest. The limit is configurable (`config :good_flows, :test_report_max_body_bytes`, default 33,554,432) so tests can use a small value. All test report limits (body bytes, both caps, read deadline, heap limit and DB timeout) are read at call time and set in `config/runtime.exs` from `TEST_REPORT_MAX_BODY_BYTES`, `TEST_REPORT_MAX_CONCURRENT_UPLOADS`, `TEST_REPORT_MAX_CONCURRENT_UPLOADS_PER_ACCOUNT`, `TEST_REPORT_READ_TIMEOUT_MS`, `TEST_REPORT_MAX_HEAP_BYTES` and `TEST_REPORT_DB_TIMEOUT_MS` (documented in `.env.sample`), except in test, which uses `config/test.exs`. The controller reads only the decoded body, not `conn.params`. No gzip/content-encoding expansion support is added in this first version.

Add OpenAPI request/acknowledgement schemas and 200, 201, 400, 401, 403, 404, 406, 408, 409, 413, 415, 422, 503 responses (406 comes from the existing `plug :accepts, ["json"]`). The OpenAPI path parameter is `project`. Do not add `"report"` to `config :phoenix, :filter_parameters`: the upload body is never parsed into params (so there is nothing to filter), and the filter substring-matches unrelated params such as `report_id` everywhere. Configure `plug Sentry.PlugContext, body_scrubber: {GoodFlowsWeb.SentryScrubber, :scrub}`, which returns `%{}` for the test-report route shape and otherwise delegates to `Sentry.PlugContext.default_body_scrubber/1`. Run payload insert and comparison queries with `log: false` so Ecto debug logs do not include the document. Validation and database errors must not render payloads. Context tests and API tests exercise the actual authenticated storage path with synthetic reports. There is no new public read route.

## Risks / Trade-offs

- [JSONB reports are larger than normalized observations] -> Bound requests, retain only requested timing data, and defer indexes/normalization until queries are designed.
- [Incomplete reports cannot later be amended] -> Collect only after writers stop; freeze local snapshots and use exact retries.
- [A private key can submit structurally valid but inaccurate reports] -> Preserve provenance and treat data as publisher-supplied; this API does not attest benchmark accuracy.
- [A stored partition is mistaken for a full run] -> Store per-report status and partition count without a whole-run completion claim.
- [Request diagnostics capture payloads] -> Add request filtering and sentinel-value assertions to controller/log/error-path tests.
- [One account fills storage with valid reports] -> Accepted risk for this first version: there is no per-account storage quota or upload rate limit. The per-account concurrency cap (default 1 per node), the body and record limits and private-key authentication bound the rate partially. Follow-up: add a per-account storage quota and/or rate limit before opening ingestion beyond trusted publishers.
- [Slow or pathological uploads exhaust slots, connections or memory] -> The read deadline (408), per-account cap, depth scan (422) and request heap limit bound each upload; the node cap stays at most half the Repo pool.
- [A publisher uploads before the project exists] -> 404. The project is the path slug. The project row must exist first. A body key `project` is 422.

## Migration Plan

Implement and deploy the server before enabling CLI publication. Apply and sync/archive `scope-recipes-by-project` first so `projects`, `GoodFlows.Projects`, and `LoadProject` exist and the canonical `projects` capability is available. This change's `specs/projects/spec.md` then modifies its deletion requirement to cover reports. The `projects` table is already created by `20261101190000_create_projects.exs`. Add one new table/migration for `test_reports`; do not alter Spry tables, the `projects` table, or rewrite existing migrations. Rollback removes the endpoint/application feature while retaining the table, or drops the new table only when explicitly accepting loss of collected reports. Companion implementation order: the project change, this server change, the `goodci` publisher, then the GoodCases configuration. Publishers put the project slug in the path and omit it from the JSON body. They must create the project before the first upload. `goodci`'s upload change still posts to `/api/v1/test-timing-reports` with a body `project`; update that contract before implementation is ready. No service is deployed by artifact creation.
